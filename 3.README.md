
## Clothing Brand Database — WorkItem3

## Overview

This project develops and evaluates a PostgreSQL database for a clothing brand. 
Part 3 focuses on database normalisation, index performance, transactions, role-based permissions, 
and database backup and restoration.

The database contains the following tables:

- `Category` — clothing product categories.
- `Product` — products and their prices.
- `Customer` — customer information.
- `CustomerOrder` — customer orders and dates.
- `OrderItem` — products and quantities associated with each order.

## 1. Third Normal Form (3NF)

The database was reviewed against the principles of 1NF, 2NF, and 3NF.

Each table stores individual values, and primary keys identify individual records. 
The `OrderItem` table uses a composite primary key consisting of `order_id` and `product_id`. 
The category, product, customer, and order information is separated into related tables to reduce duplication.

The database design follows 3NF, provided that all non-key attributes depend only on their table's key 
and there are no additional transitive dependencies.

## 2. Index Evaluation

An index named idx_customerorder_customer_date was created on the CustomerOrder table 
using the columns customer_id and order_date. The purpose of the index was to improve 
queries that retrieve orders for a specific customer and sort them by order date.

The query was tested using EXPLAIN ANALYZE before and after the index was created:

EXPLAIN ANALYZE
SELECT order_id, order_date
FROM CustomerOrder
WHERE customer_id = 1
ORDER BY order_date DESC;

## Before the Index

Before the index was created, PostgreSQL used a Sequential Scan (Seq Scan) to search the 
CustomerOrder table for rows where customer_id = 1. This means PostgreSQL scanned the table to find the matching orders.

The execution plan also included a Sort operation using the quicksort method to arrange 
the results by order_date in descending order.

The measured execution time was 0.140 ms, and the estimated total cost of the plan was approximately 35.69.

## After the Index

After the index was created, PostgreSQL changed its execution plan to use a Bitmap Index Scan on idx_customerorder_customer_date, followed by a Bitmap Heap Scan on the CustomerOrder table.

The Bitmap Index Scan used the index to identify records matching customer_id = 1. The Bitmap Heap Scan then accessed the corresponding table rows. PostgreSQL still performed a Sort operation to arrange the results by order_date in descending order.

The measured execution time decreased to 0.064 ms, and the estimated total cost of the plan decreased to approximately 14.98.

## Evaluation

The results indicate that the index improved the measured performance of the query on the sample dataset.

Execution time decreased from 0.140 ms to 0.064 ms, a reduction of approximately 54.3%. 
The estimated total query cost also decreased from approximately 35.69 to 14.98.

The most significant change was that PostgreSQL replaced the Sequential Scan with a Bitmap Index Scan and Bitmap Heap Scan. 
This indicates that the query planner considered the new index useful for locating the orders belonging to customer 1.

However, the Sort operation remained in the execution plan, meaning PostgreSQL still had to sort the matching rows by order date. 
The index therefore helped with locating the relevant records, but did not eliminate sorting in this test.

Although the measured execution time improved, the database contains a relatively small sample dataset, and the absolute time difference was only 0.076 milliseconds. Execution times can vary between runs due to caching and other system conditions. Consequently, the result demonstrates a performance improvement in this particular test, but does not guarantee the same 
improvement with larger datasets or different queries.

Overall, the index was useful for this query because PostgreSQL selected it and the measured execution time and 
estimated query cost both decreased.

## 3. Transaction

A transaction was used to update the prices of two products. 
The updates were executed between `BEGIN` and `COMMIT`, allowing the changes to be treated as one unit of work.

The transaction was verified by querying the affected products after the updates.

SQL script: `3 transaction.sql`

## 4. Roles and Permissions

A restricted PostgreSQL role named `clothing_reader` was created. It was granted permission 
to connect to the database, use the `public` schema, and read the `Category` and `Product` tables.

The role was tested by running a `SELECT` query, which succeeded, and an `UPDATE` query, 
which was denied because the role lacked update permission.

SQL script: `3 roles permissions.sql`

## 5. Database Backup and Restoration

The original database was backed up using `pg_dump` and restored into a separate database 
named `clothing_brand_restore` using `pg_restore`.

The restored database was verified by checking the number of products, customers, and 
orders and comparing the results with the original database.
